Correction — 6 August 2026 · read first

This review was written without a consumer lens, and that produced wrong verdicts. juicebox.js is an embeddable component, not an application. It is consumed by juicebox-web and Spacewalk — and, being MIT and published, by embedders we cannot see. HICBrowser is not exported from js/index.js: hosts get instances from init(), so the entire browser-instance surface is public in practice and declared nowhere.

The consequence: the deletion test cannot be answered by grepping js/. Doing so returns "no callers" for members two shipped apps depend on. Two cards asserted exactly that and were wrong — candidate 2 ("every published event has zero subscribers"; Spacewalk subscribes one) and candidate 3 ("31 members carry zero behaviour"; five are consumer API).

It has already cost a real regression: juicebox-web has subscribed to MapLoad since PR #406 shipped in v3.1.0 (Dec 2025) removed the publish. Silently dead for eight months.

Every card below now carries a Consumer impact block, measured against both checkouts at v3.6.2. The surface itself is ADR-0003. Read it before scoping any candidate.

▸ How to read this report badges · diagram vocabulary · reading order

This document does one thing: it proposes a set of refactors, each a self-contained card. Everything else is scaffolding around that list. The vocabulary below is stable across reports of this kind.

The three badges on each card

Every card's title row carries up to three chips. They answer three different questions and are easy to conflate.

1 · Status — where it stands right now
Landeddone and merged
Tracked · #nnnalready an issue in the tracker — not new work
Nextthe single recommended starting point
Opennot started, backlog
2 · Confidence — how sure the review is it's worth doing
Strongthe case is made; the evidence is in the card
Worth exploringplausible, but scope it before committing
Speculativemay not survive contact with the code
3 · Refactor shape — what kind of move it is

Always gray, so it reads as noise. It isn't — it is the best single predictor of how the work will feel.

deletion testthe win is that code disappears. Nothing is rebuilt elsewhere. Complexity vanishes, it does not move.
in-processlogic moves out of one module into another behind a real interface. Same behaviour, better boundary.
ports & adaptersseveral near-identical paths collapse into one interface with pluggable sources. Two real adapters justify the seam; one is hypothetical.
The before / after diagrams

Every card makes the same two-panel argument: left is today, right is proposed. The visual language is identical across all cards, whether the panel is an SVG or a mermaid graph.

Red fill — the problem. Tangled code, dead code, or a field that lies.
Red arrow — leakage. Something reaching across a boundary it should not know about.
Dark navy block — the deep module. Small interface on top, substantial logic hidden inside. This is the goal state in every card; it only ever appears on the right.
Dashed gray line — a seam. The new boundary being introduced, and the line the tests will run against.
White box — an ordinary module. Unremarkable, left alone.
Green — pure, tested, or extracted-and-now-testable. Free functions with no I/O and no framework.

The shorthand: how much red on the left, how much navy on the right. That is the whole picture. Card 3 is the clearest instance — six thin red bands, one per hop, become two.

Anatomy of a card
  1. Title + three badges — the claim and its standing.
  2. Monospace file list — every file the work touches. A rough proxy for blast radius.
  3. Before / after panels — the argument, in the visual language above.
  4. Problem / Solution pair — the same argument in two sentences. If you read nothing else on a card, read this.
  5. Bulleted payoff list — why it is worth it. Recurring terms: leverage (one interface replaces many call shapes), locality (one place to look instead of several), the interface is the test surface (it becomes testable without standing the whole system up).
  6. Amber box, when present — a caveat to check before starting.
  7. Green box, when present — the outcome, written after the work landed. Includes what the card failed to predict.
Suggested reading order

Not front to back. The cards are a backlog, written to be read when you reach them.

  1. The green Progress box at the top — where things stand.
  2. The Next task section — one recommendation while the candidates were queued; since candidate 9 landed it records that the queue has run out and what the landings taught.
  3. That one card. Nothing else.
  4. Reading this report now, at the very end — buried, and the most load-bearing part. It records what has drifted.

Browser lifecycle & wiring

3 · Collapse the pass-through modules around HICBrowser

Landed · #467, #468 Strong deletion test

js/browserUIManager.js · js/renderCoordinator.js · js/hicBrowser.js (31 forwarding members)

Before — six thin bands per call
caller
browser.update() 1 line
renderCoordinator.update() re-entrancy queue
browser.startSpinner() 1 line
contactMatrixView.startSpinner() DOM
browser.ui.getComponent('x') Map lookup
widget work happens

Also: activeDataset/activeState and dataset/state were two accessor vocabularies used inside one render pass — resolved in #468, canonical dataset/state with the others kept as host-facing aliases.

After — two bands
caller
browser.update() re-entrancy queue + spinner counting + fan-out widgets held as named fields
widget work happens

One accessor vocabulary. Spinner counting owned in one module.

Problem
BrowserUIManager is a stringly-typed Map with one real method, and 5 of its 13 entries are never retrieved. RenderCoordinator's body is entirely this.browser.*; the browser re-exposes all of it as identical passthroughs. Neither adds an interface — they add a hop.
Solution
Delete BrowserUIManager; hold widgets as named fields built by a createWidgets(browser) function. Fold RenderCoordinator's re-entrancy queue back into HICBrowser.update and drop the duplicate spinner hop. Drop the 13 notify* one-liners and the back-compat accessors.
  • deletion test: ~120 lines vanish with no behaviour change
  • HICBrowser has 80 members; 31 forward without adding behaviour — 18 delegations plus 14 notify*. Only the notify* half was deletable: five of the delegations are consumer API. Delivered 80 → 65 (#467)
  • stringly-typed lookup becomes field access
  • fixes nesting of spinner counts under rapid drag — update() and renderTrackXY() both start one, and the inner finally stops the shared spinner while the outer is still running
  • dead on arrival: RenderCoordinator.init() duplicates a constructor line; getCallbacksFor() and listComponents() have no callers
  • keep BrowserCoordinator — deleting it would push 300 lines back and make the god object real again
Two calling conventions are live simultaneously and both must keep working through the change: annotationWidget.js:187 calls browser.notifyTrackState2D, while hicColorScaleWidget.js:183 calls browser.coordinator.onBackgroundColorChange directly.
Outcome — landed 99c297b / 18ac88b (#467), d535e64 (#468)

#467, the subtraction. browserUIManager.js and renderCoordinator.js deleted, createWidgets.js added, 14 notify* forwarders gone. 80 members → 65, not the ~49 the card projected: the member-count target was retired rather than met, because five of the counted delegations turned out to be consumer API.

#468, the accessor vocabulary — split out so #467 stayed readable as a pure deletion. dataset/state is now what every internal call site reads. activeDataset/activeState survive as aliases carrying a JSDoc line naming the consumer, which is what stops a future cleanup pass deleting an accessor that looks unused from in here. Not marked @deprecated: that implies a removal nobody has scheduled.

What #468 did not predict: its own consumer citations were stale on arrival. It named Spacewalk's sessionServices.js as reading browser.dataset; by the time it was implemented, that read had moved to juicebox/hicMapState.js. The habit of citing file and line is right and the citations rot anyway — filed as #474.

test/testAccessorVocabulary.js keeps the vocabulary from growing back: it fails on any internal read of an alias, exempting lines rather than files so the accessor definitions pass and a stray browser.activeDataset anywhere does not.

Consumer impact — the member count below is not a target
The "31 carry zero behaviour" figure counts five members that are consumer API. loadHicFile (both apps), loadTracks and loadHicControlFile (juicebox-web), loadLiveContactMap and parseGotoInput (Spacewalk). Four of them have no internal callers at all — they exist only for hosts, so deleting them publishes dataLoader and interactions instead of removing a hop.

The notify* half was safe and is done: neither app called one. Delivered 80 → 65, not 80 → ~49; the target is retired, see #467. Also must survive: reset, config, layoutController, eventBus, coordinator (ADR-0002).

4 · Give the browser registry an owner

Landed · #476, #478–#483 Strong in-process

js/createBrowser.js · js/init.js · js/session.js · js/dataLoader.js · js/layoutController.js · js/globals.js

Before — one registry per page
After — one registry per host container
Problem
The set of live browsers is a module-level let in createBrowser.js:14, scoped to the page rather than the embed. A host calling hic.init() twice has its first browser's DOM removed by the second call, and syncBrowsers() cross-joins every browser on the page regardless of container.
Solution
An object returned by init() owns its browsers, its current-browser pointer, its sync group and its teardown. The pairing rule comes out as a free function over a list.
  • this is issue #384, open and previously undiagnosed
  • locality: "which browsers exist" has one owner instead of a file-scope variable six modules reach into
  • the interface is the test surface: today no test constructs a browser, because test N leaks into test N+1
  • gives dispose() a home — see candidate 8
  • plausibly also #280 — the sync race depends on which browser's fetch resolves first
Four page-scoped singletons ride along and must be scoped with it or deliberately left alone: the --hic-viewport-* CSS custom properties written to document.documentElement (layoutController.js:246), Globals.selectedGene, the Alert singleton re-bound per init(), and inProgressCache in contactMatrixView.js:723. The CSS variables are the hard one — two embeds cannot currently have different viewport sizes, and fixing that is a rendering change, not a lifecycle change.
Outcome — landed 78a5d0b..9fde9a2, seven issues (#476, #478–#483)

The card's solution sentence was rejected, and that is the whole design. "An object returned by init()" changes what init resolves to, which both hosts depend on. Instead a new initRegistry(container, config) is the real initialization function and returns the registry; init() became a wrapper that keeps its published return type — one browser, or an array. Reasoning and eight other decisions in ADR-0004; the ticket decomposition and which skill fits which ticket in the item 4 punchlist.

The Consumer impact box below was right about "do it additively" and wrong about the mechanism. It proposed the module-level functions delegate to a default registry. There is no default registry: registries are found through a WeakMap<Element, BrowserRegistry>, so createBrowser resolves from its container argument and setCurrentBrowser from a new browser.registry back-pointer. Only the two zero-argument getters needed a policy — getCurrentBrowser() is the most recently selected browser page-wide, byte-for-byte the old module variable, and getAllBrowsers() returns that browser's registry's browsers. Both hosts needed no change.

The card's testability argument had already half-expired — test/utils/browserFixture.js could stand up a browser before this work started. What was still true is that test N leaked into test N+1, and that is gone: 337 → 439 tests, including test/testInitRegistry.js, which stands up two real embeds in two containers and asserts the second initialization leaves the first's DOM standing, the subtrees are disjoint, and a pan reaches only its own embed. That assertion is #384, closed after two years. #475 closed with it — deleting the current browser now falls selection through to another in the same registry.

Of the four page-scoped singletons in the amber box above: Globals.selectedGene and the Alert singleton moved onto the registry (#481); inProgressCache deliberately stayed page-scoped, being keyed by URL and shared to everyone's benefit; and the --hic-viewport-* CSS custom properties stayed, as #477 — now closed. Two embeds coexist, viewport sizing included. The decision #477 needed turned out to be finer than the registry seam: the properties went to each browser's rootElement, not to the registry's container, because one container holds many browsers. No stylesheet rewrite and no ADR; the outcome is recorded in ADR-0004's scope section.

Still owed: a runtime click-through against a running juicebox-web — browser panel add/delete/select and session save. #479 was verified against the checkout statically (13 call sites, all resolving one registry) because no headless browser was available where it was built. This is the candidate's one unverified claim, and it belongs in #466's pre-release checklist rather than being left implied.

Consumer impact — changes a public return type
Highest-exposure candidate on the list. juicebox-web uses every registry export: getCurrentBrowser (10 sites), getAllBrowsers, setCurrentBrowser, createBrowser, init; Spacewalk uses getCurrentBrowser. "An object returned by init()" changes what init resolves to — today a browser or a list of them, which both apps depend on. juicebox-web also reads getCurrentBrowser().config for {width, height}.

Do it additively: the owner object is new, and the four module-level functions stay, delegating to a default registry. Otherwise this is a major version, not a refactor.

8 · Give the browser a teardown that matches its construction

Landed · #491–#496 Contract settled — ADR-0005 in-process

js/hicBrowser.js (constructor, reset, clearDataset) · js/browserRegistry.js (delete, deleteAll) · js/createBrowser.js (deleteBrowser, deleteAllBrowsers)

Settled — and the card below was wrong twice

This candidate is not breaking. ADR-0005 keeps reset()'s browser identity, so juicebox-web's reset() → loadHicFile() → enableIfMapLoaded(browser) sequence is untouched. The Consumer impact box below asked the right question; the answer is the first of its two branches.

Two of the five "Before" rows were already fixed. grep -rn subscribe js/ returns zero subscription sites outside eventBus.js — #414 migrated every internal subscription to the coordinator and added EventBus.unsubscribe(). The only subscribers left are hosts, and juicebox cannot unsubscribe those on their behalf. The bus rows have been corrected in place.

And one row was missing. There are four teardown paths, not three: clearSession() is the soft clear loadHicFile runs on its way in, which is why juicebox-web's reset() already clears state twice. ADR-0005 renames it clearDataset() and keeps it — the outcome is two verbs, not one.

Before — construction and teardown disagree
constructor installs 29 fields
rootElement → container removed ✓
InputDialog → appContainer leaked ✗
per-browser bus, host handlers retained ✗
internal bus subscriptions none left — #414 ✓
LayoutController's 4 fields stale refs, not leaks
reset() touches 7 of 29

Four teardown paths that do different things: reset(), clearDataset() (clearSession() when this was measured), registry.delete(), registry.deleteAll(). Three call unsyncSelf(); deleteAll() does not — so every restoreSession() leaves browsers holding deleted peers. That one is a live bug and lands before the refactor.

After — one symmetric pair
constructor records what it installed
dispose() removes every element it appended clears the per-browser bus only unsyncs from peers releases the registry slot
reset() = dispose + construct, same instance

One teardown. delete and deleteAll both call it. globalBus is never touched — those registrations belong to the host.

Problem
The constructor appends elements outside rootElement's subtree — notably InputDialog into the app container — but every delete path removes only rootElement. Repeated init() / restoreSession() cycles accumulate orphaned dialogs — one construction site, one read site, zero teardown — and the per-browser bus keeps host handler references alive after the browser is gone.
Solution
One dispose() on HICBrowser, symmetric with the constructor, published alongside registry.dispose(). reset() becomes dispose-then-construct on the same instance, restoring its sibling position; both delete paths delegate to it. A disposed browser throws.
  • locality: one place to add cleanup when a field is added to the constructor
  • a leaked InputDialog per session restore is real, reproducible growth — now verified: three build/delete cycles leave three orphaned igv-ui-generic-dialog-container nodes, measured in JSDOM against test/utils/browserFixture.js, no #438 required
  • pairs with candidate 4 — a registry needs something to call
  • the review gate: reset() must install a new State object, not mutate the old one, or #469's identity-based abandonment check silently stops firing
  • rootElement is appended with plain appendChild, so a naive dispose-then-construct on the first of two panels re-appends it last and the panels visibly swap
Outcome — landed 000a43a..8d50359, six issues (#491–#496)

The card's shape survived contact, which is new on this list. Candidates 2, 3 and 4 each had their solution sentence corrected before code; this one was corrected before code too, but by its own ADR-0005 rather than by the work — and what shipped is what the ADR said. dispose() is the one teardown, reset() is dispose-then-construct on the same instance, and delete/deleteAll both delegate. Four verbs became two.

The green box above was right that the candidate had shrunk, and it still grew a member. contactMatrixView installs gesture handlers on the document, which removing an element cannot take with it — found while building dispose() and fixed inside it (#494). The general mechanism the card asked for is what caught it: the constructor records what it installs outside rootElement, and dispose() walks that record. InputDialog was never the point, only the first instance.

The review gate held. reset() installs a new State, and #495 pinned it where it could actually drift — test/testRepaintDuringReset.js drives a repaint across a reset and asserts the pass is abandoned on state identity, per #469. That was the one invisible failure mode on this card and it is now a test rather than a warning.

registry.dispose() (#496) is the half the card did not have. It disposes every browser the registry owns, takes its own alert dialog down, and evicts the registry from the container WeakMap — so dispose-then-init() on the same element is a supported sequence rather than an accident. Eviction is identity-checked: a host still holding a stale registry and disposing it twice would otherwise delete the live embed's map entry, and the next init() would build a third registry over the second one's browsers, silently.

Both new members are declared, not discovered: browser.dispose and registry.dispose are in js/publicApi.js and in ADR-0003, per "absence is not permission." Tests 439 → 497. The one release note: a disposed browser now throws DisposedBrowserError rather than silently no-op'ing. Neither known host can hit it today; a third-party embedder might. Both new members are on #466's pre-release re-measurement list.

Consumer impact — asked and answered
juicebox-web calls browser.reset() and then, on the very next line, await browser.loadHicFile(config) on the same instance (initializationHelper.js:371-372).

"reset() becomes dispose-then-construct" breaks that if the browser it holds is invalidated or replaced. Either reset() keeps returning a usable browser of the same identity, or this needs a coordinated change in juicebox-web — decide which before writing code.
Answered: identity is preserved. Reconstruction happens inside the object — same instance, same id, same registry slot, same sibling position — so the host's reference stays valid and no coordinated release is needed. dispose() and registry.dispose() are new published members and go into js/publicApi.js with the change. The one behavioural change worth release notes: a disposed browser now throws rather than silently no-op'ing, which neither known host can hit today.

9 · Give the config schema one reader

Landed · #531–#536 One decision settled — ADR-0008 in-process

js/createBrowser.js (setDefaults) · js/hicBrowser.js (constructor, init) · js/dataLoader.js · js/browserUIManager.js · js/urlUtils.js (fixDefaults)

Before — seven readers, no schema
After — normalize once, read everywhere
Problem
No file states what a config contains. Seven modules each interpret a subset and apply their own defaults, so the entry points have silently diverged: syncDatasets is honoured by createBrowserList but not createBrowser, and fixDefaults runs on the URL path but not on restoreSession — the documented public API.
Solution
One pure normalizeConfig at the entry, producing a resolved config. Downstream modules read fields and never default.
  • the interface is the test surface: config handling becomes object-literal-testable
  • the asymmetries become visible instead of spread across seven files
  • setDefaults is already pure — it just isn't exported
  • documents the config schema by being it
  • pairs naturally with candidate 5 — decode, then normalize
Outcome — landed f08ece8..9bc9583, six issues (#531–#536)

The card's shape held: one stage, and consumers that read fields. js/normalizeSession.js is the reader, run once per session at the entry — BrowserRegistry.restoreSession for a session, createBrowser for a single browser config — and browser creation below it normalizes nothing. Three card corrections, all from candidate 5 landing or candidate 3: normalizeConfig already existed in createBrowser.js (browser-shaped and unexported), so #532 deepened it rather than inventing it and named the result normalizeSession; fixDefaults had moved to sessionCodec.js, not urlUtils.js; and js/browserUIManager.js no longer exists. Tests 731 → 881.

"Documents the config schema by being it" was half right, and the missing half is a deliverable. The stage is the executable copy, but a reader still needed prose — so CONTEXT.md now carries the resolved-config schema: every field, what is defaulted and to what, what is coerced from string form. The part nobody could have enumerated from the code is the exceptions: three fields are honoured on one path only and cannot be resolved by the stage. queryParametersSupported is read before normalize, to decide whether the address bar replaces the config at all; width/height are page-scoped (#477); and config.normalization is checked against the loaded dataset's own set, which does not exist until a dataset is loaded.

"May not need its own ADR" held for five tickets and broke on the sixth. #531–#535 were moves against ADR-0006 decision 8. #536 hit the question decision 8 does not answer: HICBrowser read miniMode as a figure mode and the stage did not, so browser.figureMode was true while the three display flags defaulted on — every entry path agreeing with the others and none with itself. Picking a winner is consumer-visible, so it got ADR-0008: figureMode wins by absorbing miniMode, and a mini map is a figure. Neither host app names miniMode in source.

The gate's own acceptance criterion was wrong on the last ticket, and the reason generalizes. Every ticket carried "#531's snapshots come back byte-identical"; #536 moved 63 of them and could not have done otherwise. A default moved up into the stage becomes a field of the resolved config, and the resolved config is what is snapshotted. The diff was tallied line by line: synchable and backgroundColor appear everywhere with no behaviour change, one fixture moves behaviourally (the miniMode decision), and one query fixture's displayMode moves to a value init() was already writing a line later. This is #533's lesson again — collapsing duplicated rules into a shared stage necessarily widens them, and widening is visible.

The two "different questions" turned out to be one. #533 kept DataLoader.loadTracks's annotation-conditioned defaults beside the stage's, on the argument that the loader owned what the load discovers. It did not: the type those rules keyed on is a field of the config. The real gap was that a track added at runtime through the published browser.loadTracks met no stage at all — so tracks got a door of their own, HICBrowser.loadTracks resolving through normalizeTrackConfigs, and the second copy went. What is left in the loader is genuinely load-discovered: a track's height from the live layout, and autoscale from a missing max.

Consumer impact — the config object is the entry contract
The config passed to hic.init(container, config) is the most-used public surface there is: juicebox-web passes a full juiceboxConfig, Spacewalk passes {} and drives everything through restoreSession. A normalizeConfig that tightens validation will reject configs that work today.

Also: juicebox-web reads browser.config back off the instance, so the resolved config is observable too — normalising it changes what that read returns.

State, session & data loading

5 · One decoder for session and URL

Landed · #499–#509 Contract settled — ADR-0006 ports & adapters

js/urlUtils.js · js/session.js · js/hicState.js (parse/fromJSON/stringify) · js/dataLoader.js · js/createBrowser.js

Before — eight encodings, three write-only
blob:<BGZip> detection — written 3×
urlUtils.js:64 · :71 · :87 — same 4 lines, three error messages
state format detection — written 2×
dataLoader.js:112 · :233 — already drifted; one has no unknown-type branch
shortcut expansion — written 2×
session.js:46-77 re-walks what urlUtils.js:196,205,262 already did
3 state decoders · 4 config decoders
parse · fromJSON · sync — extractConfig · decodeQuery · restoreSession · createBrowserList
no encoder at all for 4 formats
query config · track pipe-string · juicebox={},{} · juiceboxURL
State.stringify has zero callers — dead encoder, live decoder
After — one decode, adapters at the edge
decodeSession(input) — one interface
adapters: query string | session JSON | compressed blob | legacy state token
one error contract · one shortcut-expansion pass · one place a new format is added
sniffFormat(string) — pure
blob / data / JSON / legacy-token, extracted from three async wrappers
decodeState(input) — pure
the parse / fromJSON / default ladder, one place, tested with literals
encodeSession — the missing inverse
round-trip becomes a property test: decode(encode(x)) === x
network I/O (bitly, file fetch) moves to the caller
Problem
There is no single parse. Eight encodings of the same seven canonical fields are decoded by three state decoders and four config decoders, with blob detection written out three times and state-format detection twice — the two copies have already drifted. extractConfig is async across ~90 lines of which two do I/O, so none of the format logic is reachable from a test.
Solution
One decodeSession interface with an adapter per wire format; lift format sniffing and the state-decode ladder out as pure functions; write the missing encoder so round-tripping is testable.
  • four adapters justify the seam — this is not a hypothetical one
  • leverage: adding a format touches one module instead of four
  • the pure ladders become testable with string literals — no network, no DOM
  • a round-trip property test is the single highest-value test this repo could add
  • save → restore is not currently the identity: the State constructor transposes axes when chr1 > chr2, which is reachable at runtime
docs/url.md documents a track pipe-string layout that does not match the parser (3 tokens vs the parser's 4; the param is track in the doc, tracks in the code at urlUtils.js:184). Decide which is authoritative before collapsing the decoders — juicebox-web may generate URLs against either reading. These are public, shareable URLs; a decoder change is a compatibility change.
Settled — the parser is authoritative, and url.md is now the spec

#501, per ADR-0006 decisions 2 and 5. docs/url.md is a versioned specification rather than a description: v0 and v1 are both documented and both supported, tracks is plural, the track string has four fields, and the v1 state string carries nine tokens. State.stringify() — zero callers in all three repos, and the last executable copy of v1 — was deleted in the same commit, with the wire-format tests in test/testState.js taking over as the executable half.

The card named two drifts; there were three. Beyond track/tracks and the track field count, url.md documented a seven-token state while the decoder had a nine-token branch nothing in this repo had written since March 2025 — the two extra tokens are the view width and height, retired when the state stopped carrying them. Writing the spec surfaced two more, both filed rather than fixed here: a bare-threshold colorScale decodes to NaN RGB (#514), and an empty data-range field decodes to NaN bounds (#515).

Outcome — landed 7d93be4..683ed54, eleven issues (#499–#509)

The card said internal duplication; the work found a contract with users, and that reframing is the whole outcome. ADR-0006 opens with six facts read out of the checkout, and the first one moved the ground: State.stringify() had zero callers in all three repos, and every format the decoder accepts except session=blob: is read-only legacy inbound. The card's "no encoder at all for 4 formats" is true and is not a gap to fill — those are formats we deliberately stopped writing. So one encoder shipped, for the session-JSON form only. Writing four would have resurrected State.stringify as a live encoder for a format nothing has written in years, and we would own it forever.

The seam landed where the card drew it. js/sessionCodec.js is 950 lines holding every decision about what a session URL means; js/urlUtils.js is 60 lines holding the one read that path may need. sniffFormat and decodeState are pure and driven from string literals (#504), decodeSession takes an injected loader so the whole decode path runs with no network and no DOM (#505), and a new format is now one entry in WIRE_FORMATS. encodeSession and decode(encode(x)) === x shipped in #507. Tests 497 → 731.

Three fixes had to land before the refactor could be tested at all, and two were live bugs with no session involved. chr1 ≤ chr2 became a real invariant enforced in setView (#499) — before it, any goto whose y-axis chromosome index was below the x-axis's rendered one way and reloaded transposed. browser.toJSON() returned the string "{}" for a browser with no dataset, so saving a session while any panel was empty produced one that could not be reloaded (#500). Both legitimately move decoded output, which is why they gated the snapshot rather than following it.

The gate worked, and it is the part worth copying. #503 snapshotted today's decoder over the whole corpus before one line of decoder code moved; #504–#507 then passed by coming back byte-identical. Exactly one snapshot moved deliberately across the candidate — harvested-juiceboxURL-bitly, when #506 dropped the bit.ly format — and it is logged in the golden file's movement table with the decision that authorised it. Hand-written assertions were rejected precisely because they would have blessed a misreading as spec, and this decoder had already drifted from its own documentation in three places.

The one deliberate break, and it was not the dead path the ADR assumed. ADR-0006 justified dropping juiceboxURL= partly on the claim that its mojibake bearer token would draw a 401. Measured during #502 on 9 August: bit.ly expanded the link and the two-browser session decoded in full. The drop stands — nothing writes the format, it cannot be tested without the network, and its brace-repair bug mangles any multi-browser link from browser 2 on — but the ADR's consequences section was corrected to say that #506 removed live behaviour, and the corpus carries the fixture that says so.

What the corpus is evidence of, and what it is not. #502 harvested from the three repos and the docs; #509 went outside them to the issue trackers, on a recorded stopping rule of source-exhaustion over a fixed list. It found one shape the corpus did not already carry: a numeric seventh state token that decodes to a normalization name no .hic file has (#528). Papers, GEO and 4DN were deliberately not searched — #509 was written to run before the collapse so a late quirk could be designed in rather than patched on, and that window shut at #505. The external population beyond our own trackers has therefore never been sampled, and that gap is recorded rather than implied.

Eight follow-ups were filed rather than fixed, per the standing file-and-keep-refactoring rule: #510 (State.default() passes six arguments to a seven-parameter constructor), #514 and #515 (NaN from a bare-threshold colorScale and an empty data-range field), #518 (the session= format has a second decoder in Spacewalk that accepts a different set), #519 (the session=<File> branch is unreachable from its only caller), #521, #525 and #528. Decode/normalize is drawn as a seam here and deliberately not crossed — that is candidate 9's, and shipping both at once would double the blast radius on hic.init.

Consumer impact — the wire format is a user-facing contract
restoreSession, compressedSession and toJSON are used by both apps. Beyond the call signatures, the encoded session format is public in a stronger sense than any method: users share sessions as URLs, so a link pasted last year must still decode. Round-tripping has to stay compatible in the decode direction even if the encoder changes.

The report already names this the strongest ADR opportunity, and it is right — but the reason is the external consumer, not the internal duplication. Write the ADR before the refactor, not after.
Answered: not breaking for the archive. restoreSession, compressedSession and toJSON keep their signatures; decodeSession and encodeSession stay internal, because adding a decoder to the public surface would create a second, weaker contract we would then owe compatibility to. Decode stayed compatible in every direction but one deliberate drop (juiceboxURL=, #506), and the chr1 ≤ chr2 fix only stops new sessions being written in the unordered spelling — the constructor already transposed, so links in the wild decode exactly as they did. One accepted asymmetry: a session saved while a panel was empty now restores with one fewer panel rather than failing to restore at all, so browser count does not survive that round trip. The ADR was written before any ticket, as the card asked.
