Pixel size, bin size and the size of the screen

A Juicebox view is six numbers. The size of the screen is not one of them. That is why resizing a map is a design decision, and why, today, a resize fires no event at all.

This document works through one question: a view is showing a locus at 640 × 640 pixels, and the viewport grows to 1024 × 1024. What changes in the state, and what is announced?

The answer depends on three ideas, which the first sections cover in order: the two numbers that set the scale, what the state holds and what it leaves out, and how a resolution is chosen. The resize itself is in section 6, and the events in section 7.

1Two numbers set the scale

A .hic file stores each contact matrix several times, at a ladder of bin sizes: 2.5 Mb, 1 Mb, 500 kb, down to 5 kb or 1 kb. One bin is one cell of the matrix. Choosing a rung of that ladder is choosing a zoom, and the zoom fixes the bin size.

The pixel size is how many screen pixels one bin is drawn across. It is the second, independent dial. Together they give the only scale that matters to the eye: base pairs per screen pixel.

pixelSize is fractional. 1.28 is a legal value. Image tiles are laid out on the integer part, and the fraction is applied when they are painted.

Because the scale is a ratio, the same view on screen can be reached by changing either dial. That freedom is what makes resizing ambiguous: when the screen grows, either dial, or neither, can absorb the change.

2The state holds six numbers, and not the screen

Everything Juicebox shows is derived from the canonical state on State in js/hicState.js. The view is fixed by six of its fields; the seventh, normalization, chooses how counts are coloured.

The state string once carried the viewport too. Version 1 of the URL format had seven tokens before normalization, the fifth and sixth being view width and height. State.parse still reads v1 strings and drops those two.

The viewport size is held by the page, as the CSS custom properties --hic-viewport-width and --hic-viewport-height on the browser’s root element. They are written once, at construction, from the config’s width and height, and default to 640. Juicebox reads the size back from the DOM, as viewportElement.offsetWidth, whenever it needs it.

A saved session does not record it either. HICBrowser.toJSON() writes the state, the map’s URL and its colours, and no width or height.

3From state to locus

x and y are the bin at the top-left corner of the viewport, not its centre. Everything to the right of it is measured in bins, which the pixel size turns into pixels.

4How a resolution is chosen

When a host or a user asks for a locus, Juicebox has a target scale and must choose both dials. It does it in three steps, in State.updateWithLoci:

  1. Compute the target scale: bpPerPixel = max(rangeX ÷ width, rangeY ÷ height). The width is read from the viewport at that moment.
  2. Choose the finest rung whose bin is at least that large (findMatchingZoomIndex). A bin is never smaller than a pixel.
  3. Set pixelSize = binSize ÷ bpPerPixel, which is therefore always 1 or more.

The plot below is the whole space of views. Each rung of the ladder is a vertical line; moving up a line magnifies its bins. A diagonal is a constant scale, so every point on one diagonal shows the same stretch of genome.

The floor is not always 1. browser.minPixelSize raises it so that a whole chromosome at the current rung still fills the viewport, and that calculation reads the viewport’s width.

Two consequences follow. A larger screen showing the same locus needs a finer scale, and if the lock is open the finer scale usually means a finer rung: new data, new tiles. And the rung is chosen against the width at the moment of the request, so the same request at two widths can load two different resolutions.

5Where the screen size leaks into the state

The viewport is not stored, but it is read whenever the state is written. These are the places, all in the write path, that consult it. Each uses the width at the moment of the write and none is re-run when the width changes later.

6Resizing from 640 to 1024

The viewport grows from 640 to 1024 pixels square, 1.6 times wider. The ratio bpPerPixel can stay or change, and the origin can stay or move. That gives three reasonable policies, and each one is what some application does.

The same three, as numbers. The bin size, pixel size and origin are what a session would save; the locus is what the locus box would show.

7What fires

Resizing the viewport fires nothing. No code in juicebox.js observes the viewport’s size: there is no ResizeObserver and no window resize listener. Events fire only when something writes the state.

Here is the machinery, and the three ways into it.

Peers are resynced on every update(), whatever caused it. That is safe after a resize: getSyncState sends the origin, bin size and pixel size, not the locus, and A changes none of them.

The middle entry of Figure 6 is the subtle one. If a host enlarges the viewport and calls update(), the map repaints correctly under policy A, but the locus box still shows the old end, 48,000,000, and the host’s onLocusChange callback never hears that the visible locus is now 40.0–52.8 Mb. The locus changed without a locus change.

A is cheapest for the renderer and dearest for honesty: no translator runs, so nothing would call onLocusChange unless the resize code called it itself. B is a pan, panShift, and gets the whole path for free. C is a goto, which also clears the image cache; done on every frame of a drag it would refetch the map continuously.

Image tiles are cached by what they contain: chromosome pair, bin size, grid position, normalization. Not by pan position or pixel size. A and B reuse every tile they already have.

8Juicebox already answers the question, twice

Two existing features meet a view of one size at another size. Both behave like policy A.

Sessions. toJSON() saves the state and no size. A session saved at 640 and opened in a 1024 viewport opens at the same corner and scale, and shows more. Spacewalk works around the other half of this in src/juicebox/panelDimensions.js, by writing its panel’s width and height into every browser config before a session reaches Juicebox.

Sync groups. State.sync receives the publisher’s origin in base pairs and its binSize ÷ pixelSize. The receiver keeps the scale, not the extent. Two synced browsers of different sizes agree on their top-left corner and scale, and the larger one shows more.

Policy A therefore costs nothing new to explain, and it leaves synced peers where they are. B and C do not stay local: both write the state, and update() publishes it. Under B every peer pans by the same distance in base pairs, though only one browser was resized. Under C every unlocked peer zooms to the new scale, though its own viewport did not change.

9If resizing is built

A resize is a change of the viewport followed by a state write through a translator. Without the write there is no announcement. A sketch:

  1. Change the size. Write --hic-viewport-width and --hic-viewport-height on the browser’s root, as setViewportSize in js/layoutController.js does at construction. Keep the viewport square: a non-square viewport is not supported (CONTEXT.md).
  2. Re-lay out. Resize the track canvases and rulers to match. updateLayout() does this, and repaints.
  3. Write the state through a translator, chosen by policy: none for A; panShift(−Δw/2, −Δh/2) for B; goto with the old locus for C. The translator reads the new width, so it must run after step 1.
  4. Announce. For B and C the translator announces itself. For A, call onLocusChange with both change flags false, so the locus box and the host see the new extent.

A recommendation, given what already exists. Use A while a drag is in progress: it writes nothing, reuses every cached tile, moves no peer, and is already what a saved session does. Announce once when the drag ends. If the host’s contract is a locus, as an MCP tool’s or a figure’s is, apply C at that moment instead, once and not on every frame, and accept that synced peers will follow the new scale.

A drag fires many resizes. update() already coalesces calls that arrive while a repaint is in flight, so the repaint keeps up. The tile fetches of a C-on-every-frame would not.
